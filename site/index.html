01 / THE INVESTMENT THESIS

A focused entry point. A larger ambition.

Shared hardware.
Explicit isolation.

Our thesis: accelerator teams will need better ways to control which workloads can access memory and consume resources. Aether starts with that boundary, rather than asking a customer to adopt an entire operating system.

01 — THE PROBLEM TO VALIDATE

Sharing creates
an integration burden.

Runtime teams must manage access, interference and failure containment across workloads. We’re testing where existing vendor tools and custom runtime code leave a costly gap.

02 — OUR APPROACH

Make the boundary
part of the contract.

A capability model gives memory and accelerator operations explicit permissions. Software demos reject named unauthorized requests and model resource partitions.

03 — THE NEXT PROOF

One buyer.
One useful integration.

Evaluate one workload against a customer’s current approach. Measure containment, overhead and integration effort in an agreed environment.

WHY THIS OPPORTUNITY MATTERS

The risks we’re working to resolve

Hardware & security boundaries

Real accelerator isolation and runtime integration remain unvalidated. Issue #161 (unchecked raw unmap helpers) is fixed in the Soft SMMU: unmap now requires a Memory+MAP capability and a foreign tenant's pin is refused with CrossTenant; the bounded fuzz now exercises these paths. No formal verification is claimed.

Demand & purchasing

The buyer, urgency, budget and willingness to pay are hypotheses. No verified customer commitment, paid pilot or revenue is claimed.

Adoption & repeatability

Aether must fit the buyer’s existing stack and outperform its workaround on agreed criteria. Integration effort and reuse across a second buyer must be measured before assuming product economics.

WHAT WE WOULD EVALUATE

One bounded question.

  • Unauthorized access refusal, with valid controls.
  • Fault containment while a legitimate workload runs.
  • Overhead against the buyer’s current approach.
  • Recovery behavior and integration hours.
WHAT A PARTNER WOULD PROVIDE

Access and an engineer.

  • One workload and supported environment.
  • A named technical owner and baseline.
  • Hardware or interface access where needed.
  • Written thresholds and an evaluation end date.

Proposed deliverables: integration component, reproduction bundle, evaluation report and documentation. Scope, fee and acceptance are agreed together. A software-only evaluation cannot establish hardware isolation.
