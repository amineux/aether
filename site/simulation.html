THE PROPOSED MECHANISM

A lease with
an expiration boundary.

Bind a data grant to a tenant, a byte range, read permissions and an epoch. When the epoch advances, a stale grant fails the next admission check. A neighboring tenant keeps its own lease.

Browser protocol sketch. In-flight DMA draining, hardware invalidation and race-safe kernel integration remain open work.

How are the numbers calculated?

Transfer time T = bytes / bandwidth. Compute C = 200 μs × read passes. Home wait W = C × contention / (1 − contention).

Copy: T + C. Local lease: setup + W + C. Remote lease: setup + passes × T + C. The planner picks the lowest modeled completion time; ties favor copying.

A 32-byte grant is inspired by the existing toy KV demo. Actual local data reads still occur. Remote leases still transfer the requested bytes; permission does not make data movement disappear.

What exists in Aether today?

The repository has a capability fabric, a software KV-grant demo, scoped fences and software isolation tests. LeaseLab adds a browser model and a proposed epoch protocol. It does not implement this planner in the kernel.

What would prove or disprove this idea?

Replay real workload traces on an accelerator backend. Measure transfer bytes, p50/p99 latency, setup overhead and fairness. Test revoke-versus-submit races and drain in-flight DMA before memory reuse. Reject the thesis if overhead or contention erases the benefit.

This serial model omits overlap, cache effects, topology, power and real queue distributions. It establishes neither novelty nor superiority over existing systems.
